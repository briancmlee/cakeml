# D39: Proxy learns the backend's status without the client gate

Status: **decided (user, 2026-10-17, via the desk; Q-8)**

User's words: "yeah for Q-8 lets do (a)".

**Option (a): program change.** In the step-9 proxy statement (rev 7, spike/moonshot-step9-stmts @44aef7635,
`async/moonshot-step9/hl/proxyHLStmtsScript.sml`, `proxy_guar_hl`), the backend's FIRST read (its settle read,
which tells the proxy whether the connect came up or was refused) is not gated by the client's Level. The
credit-gate clause for the backend applies only once the backend has answered (`hl_up c`). The proxy program
`pstep` (moonshotProxy, and m4-server's translated copy on spike/proxy-fold) changes to match.

Why: rev 7's pairing-liveness clause ("every accepted client gets a backend that comes up or is refused, unless
connects keep returning no socket") could not be met by any program. If the backend refuses every connect and
the client's Level always reads above hw, the credit gate forbids ever reading the backend, so the proxy never
learns of the refusal (finding F-pair-lv, honest-ffi). A real proxy learns a refused connect from connect
completion, whatever the client's buffer level ("make L1 robust like a real server").

Effect on the buffer bound (hw + pf_chunk + pread): none. Before the backend's first answer nothing from it has
been written to the client, so in a real run that read passes the gate anyway. Cost: about 2–4 h of proof
repair plus the same change in the translated proxy. No trusted definitions change.

Rejected: (b) excuse "unless the client's Level answers exceed hw from some round on" (no cost, but gives up
noticing a refusal while the client is slow, which a real proxy would notice); (c) a hypothesis restricting the
Level oracle (a rely, not an observation). Challenge record: the orchestrator pushed back on honest-ffi's
original recommendation (b); asking (a)'s cost and bound effect changed the recommendation to (a).
